1. 总流程：从“状态变化”到“屏幕变亮”
当列表 ABCD 变成 ADBC 时，React 不会粗暴地删除重建，而是经历两个严格的阶段：
Render（渲染）阶段：“找不同”。这个阶段可中断，负责算出“谁需要动”。
Commit（提交）阶段：“施工”。这个阶段同步且不可中断，负责把变化真实地反应到 DOM 上。
2. Render 阶段：Diff 算法只问“动不动”
在这个阶段，算法拿着新旧两个列表，只做一件事：用 lastPlacedIndex（上次最大索引）规则，给节点打标记。
遍历新列表 [A, D, B, C]，查找它们在旧列表中的位置。
A（旧0）和 D（旧3）按顺序递增，不动。
B（旧1）和 C（旧2）发现自己的旧索引小于当前的 lastPlacedIndex（即3），被判定为 “需要移动”。
结论：此时算法根本不管 B 和 C 要挪到哪，只是简单地在它们身上贴了个 “待施工” 的标签。
3. Commit 阶段：“新列表的兄弟节点”就是施工蓝图
进入真正操作 DOM 时，算法彻底忘掉旧列表和物理 DOM 当前的混乱状态，完全依照新 Fiber 树（虚拟 DOM） 中的关系来操作：
铁律：任何移动都通过 parentNode.insertBefore(节点, 下一个兄弟节点) 实现（如果下一个兄弟是 null，则用 appendChild）。
逆序处理：为了保证不覆盖，先处理 C，再处理 B。
移 C：看新列表，C 的下一个兄弟是 null（末尾） → 执行 appendChild(C)，C 跑到末尾（物理 DOM 暂时为 A-B-D-C）。
移 B：看新列表，B 的下一个兄弟是 C（注意，此时逻辑上 B 的兄弟永远指向 C，算法不看物理 DOM 上 B 旁边是谁） → 执行 insertBefore(B, C)，浏览器自动把 B 剪切并插到 C 前面。
4. 整个机制最精妙的两个设计点
职责解耦（你的核心顿悟）：Diff 只负责“判叛变”（数值比较），Commit 只负责“看地图”（读取 Fiber 节点的 sibling 指针）。两者互不干扰，避免了计算“相对位移”的复杂逻辑。
物理 DOM 只作为“被操作的肉”：Commit 阶段完全不依赖物理 DOM 的当前结构来决策（比如不看 B 现在挨着 D）。它只把物理 DOM 当作一个任由 insertBefore 暴力“剪切+插入”的容器，浏览器的原生 API 会保证最终顺序绝对正确。
最终结论
Diff 阶段找“谁要动”，Commit 阶段根据“新列表里的邻居是谁”决定“动到哪”。 这两者结合，让 React 用最少的 DOM 操作（本例仅 2 次移动）和极简的算法逻辑，高效地完成了界面的更新。
