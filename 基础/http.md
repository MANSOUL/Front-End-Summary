HTTP（HyperText Transfer Protocol，超文本传输协议）是应用层协议，用于客户端和服务器之间传输超文本、JSON、图片等资源。它采用请求-响应模型：客户端发请求，服务器返回响应。默认端口 80，HTTPS 默认 443。

核心特点

· 应用层协议：通常基于 TCP，HTTP/3 基于 QUIC/UDP。
· 无状态：每个请求独立，服务器默认不记录上下文；靠 Cookie、Session、Token 维持状态。
· 可扩展：方法、头部、状态码都可扩展。
· 媒体无关：用 Content-Type 标识资源类型，如 application/json、text/html。
· 明文传输：HTTP 本身不加密，HTTPS 通过 TLS 加密。

报文结构

请求报文：

```http
GET /api/users/1 HTTP/1.1
Host: example.com
Accept: application/json
```

响应报文：

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27

{"id":1,"name":"Alice"}
```

格式都是：起始行 + 头部 + 空行 + 主体。

常见方法与语义

· GET：获取资源，安全、幂等。
· POST：提交数据或创建资源，非幂等。
· PUT：全量更新，幂等。
· PATCH：部分更新，通常非幂等。
· DELETE：删除资源，幂等。
· HEAD：只要响应头，不要主体。
· OPTIONS：查询支持的方法，CORS 预检常用。

状态码分类

· 1xx：信息性。
· 2xx：成功，如 200、201、204。
· 3xx：重定向，如 301、302、304。
· 4xx：客户端错误，如 400、401、403、404。
· 5xx：服务器错误，如 500、502、503。

常见头部

· Host：目标主机，HTTP/1.1 必需。
· Content-Type / Content-Length：主体类型和长度。
· Cookie / Set-Cookie：状态管理。
· Authorization：认证信息。
· Cache-Control、ETag、Last-Modified：缓存控制。
· Connection：连接管理。

版本演进

· HTTP/1.0：短连接，每个请求新建 TCP。
· HTTP/1.1：默认持久连接、Host 头、分块传输；存在队头阻塞。
· HTTP/2：二进制分帧、多路复用、头部压缩 HPACK，解决 HTTP/1.1 应用层队头阻塞；TCP 层仍有队头阻塞。
· HTTP/3：基于 QUIC/UDP，0-RTT 建连，解决 TCP 队头阻塞，弱网表现更好。

缓存与 HTTPS

· 强缓存：Cache-Control、Expires。
· 协商缓存：ETag / If-None-Match、Last-Modified / If-Modified-Since，命中返回 304。
· HTTPS：HTTP + TLS，提供加密、完整性校验和身份认证，防止窃听和篡改。

一句话

“HTTP 是应用层请求-响应协议，无状态，通常基于 TCP，HTTP/3 基于 QUIC。它通过方法、状态码、头部和主体表达语义。HTTP/1.1 是持久连接，HTTP/2 多路复用，HTTP/3 用 QUIC 解决队头阻塞。HTTP 本身明文，HTTPS 加 TLS 实现安全。RESTful 是基于 HTTP 的架构风格，不是协议本身。”


多路复用和队头阻塞是 HTTP 性能演进的核心概念。简单说：多路复用是为了解决队头阻塞，但 HTTP/2 只解决了应用层队头阻塞，TCP 层队头阻塞要靠 HTTP/3 解决。

1. 什么是队头阻塞（HOL Blocking）

队列里前面的任务卡住了，后面的任务即使已经就绪，也只能干等。

在 HTTP 场景中分两层：

· HTTP/1.1 应用层队头阻塞
    一个 TCP 连接上，请求虽然可以管道化发送，但响应必须按请求顺序返回。如果第一个请求处理很慢，后面请求的响应就算好了，也不能先发，只能排队等。浏览器为了绕过，通常对同一域名开 6 个左右 TCP 连接，但连接数有限，高并发下依然会堵。
· TCP 层队头阻塞
    TCP 是可靠字节流，必须按序交付。如果某个 TCP 段丢包，后面的段即使已经到达接收端，内核也不会交给应用层，必须等丢包重传成功。这会导致这条 TCP 连接上所有数据都被阻塞。

2. 什么是多路复用（Multiplexing）

在 HTTP/2 中，在单个 TCP 连接上同时传输多个独立的请求/响应，互不干扰。

实现方式：

· 把每个请求/响应拆成二进制帧。
· 每个帧带上 Stream ID，标识它属于哪个流（一个流对应一个请求/响应）。
· 不同流的帧可以交错发送，接收端根据 Stream ID 重新组装。
· 流还有优先级、流量控制等机制。

这样，一个请求慢，不会阻塞其他请求的帧传输。应用层的队头阻塞被消除了。

3. 为什么 HTTP/2 还没完全解决？

HTTP/2 多路复用跑在单个 TCP 连接上。TCP 不认识 Stream ID，它只看到一串字节。一旦发生丢包，TCP 必须等待重传，所有流的数据都被卡住——这就是 TCP 层队头阻塞。所以 HTTP/2 解决了 HTTP/1.1 的应用层队头阻塞，但没解决 TCP 层的。

4. HTTP/3 怎么解决？

HTTP/3 改用 QUIC（基于 UDP）。QUIC 在用户态实现了可靠传输，但每个流独立处理丢包：

· 流 A 丢包，只重传流 A 的数据，流 B、C 不受影响。
· 建连更快（0-RTT/1-RTT），还支持连接迁移。

这样才真正解决了传输层的队头阻塞。

5. 一个比喻

· HTTP/1.1：单车道隧道，前车慢，后车全堵。
· HTTP/2 多路复用：把一辆辆大车拆成小包裹，多个车道的包裹混在一起过同一条隧道。包裹按编号重组，应用层不堵了。但隧道本身只有一条，隧道塌方（丢包），所有包裹都过不去。
· HTTP/3：每个车道独立隧道，一条塌方不影响其他车道。

一句话

“队头阻塞是队列前部阻塞导致后部无法处理。HTTP/1.1 有应用层队头阻塞，响应必须按序返回；TCP 有传输层队头阻塞，丢包会阻塞整条连接。HTTP/2 通过二进制分帧和 Stream ID 在单 TCP 连接上多路复用，解决了应用层队头阻塞，但 TCP 层仍存在。HTTP/3 基于 QUIC，每个流独立处理丢包，才彻底解决。”


HTTPS 的本质是 HTTP over TLS，也就是在 HTTP 和 TCP 之间加了一层 TLS/SSL。它不改变 HTTP 的语义，只是把 HTTP 报文放进一个加密、可认证、防篡改的通道里传输。默认端口 443。

一、HTTPS 要解决三个问题

1. 机密性：数据不能被窃听。
2. 完整性：数据不能被篡改。
3. 身份认证：确认对方真的是目标服务器，而不是中间人。

实现思路是：用非对称加密和证书完成身份认证与密钥交换，再用对称加密传输数据，用 MAC/AEAD 保证完整性。

二、整体流程

1. TCP 三次握手建立连接。
2. 进行 TLS 握手，协商版本、密码套件，验证证书，生成会话密钥。
3. 之后所有 HTTP 数据都用会话密钥对称加密传输。
4. 连接关闭。

三、TLS 握手核心步骤（以 TLS 1.2 为例）

1. ClientHello
      客户端发送：支持的 TLS 版本、密码套件列表、客户端随机数 Client Random、SNI（目标域名）等。
2. ServerHello
      服务器选定 TLS 版本和密码套件，返回服务器随机数 Server Random。
3. 服务器发送证书链
      包含服务器公钥、域名、有效期、CA 签名。客户端验证：
   · 证书是否由受信任的 CA 签发；
   · 域名是否匹配；
   · 是否在有效期内；
   · 是否被吊销（CRL/OCSP）。
4. 密钥交换
      这是关键。分两种常见方式：
   · RSA 密钥交换：客户端生成预主密钥，用服务器公钥加密后发给服务器，服务器用私钥解密。双方再用 Client Random + Server Random + Pre-Master Secret 生成会话密钥。缺点：没有前向安全。
   · ECDHE 密钥交换：双方交换椭圆曲线参数，各自计算出共享密钥。即使服务器私钥泄露，过去的会话也解不开，具备前向安全。
5. 生成会话密钥
      双方用共享秘密和随机数派生出对称密钥，之后用对称加密（如 AES-GCM、ChaCha20-Poly1305）传输数据。
6. Finished
      双方发送 Finished 消息，验证握手过程没有被篡改。之后开始加密通信。

四、TLS 1.3 的改进

TLS 1.3 大幅简化并强化了握手：

· 只保留 ECDHE/PSK 等安全密钥交换，去掉 RSA 密钥交换。
· 握手通常只需 1-RTT，会话恢复可 0-RTT。
· 证书和更多握手信息也被加密。
· 强制前向安全，移除弱算法。
· 基于 QUIC 的 HTTP/3 内置 TLS 1.3。

五、证书与 CA 的作用

服务器公钥是公开的，问题在于：怎么确认这个公钥真的属于目标网站？
靠 CA（证书颁发机构）。CA 用自己的私钥对服务器证书签名，浏览器和操作系统内置了根 CA 公钥。客户端沿着证书链逐级验证签名，最终信任到根 CA。这样就能防中间人伪造证书。

六、加密算法分工

· 非对称加密：用于身份认证和密钥交换，计算慢。
· 对称加密：用于实际数据传输，计算快。
· 哈希/HMAC/AEAD：保证数据完整性，防止篡改。
· 数字签名：证书验证，确认服务器身份。

七、和 HTTP/2、HTTP/3 的关系

· HTTP/2 通常跑在 TLS 上，浏览器要求 HTTPS。
· HTTP/3 基于 QUIC，QUIC 内置 TLS 1.3，天然加密。

一句话

“HTTPS 就是 HTTP 加 TLS。它先通过 TCP 建连，然后 TLS 握手：客户端发 ClientHello，服务器返回证书和 ServerHello，客户端验证证书链，再用 ECDHE 或 RSA 交换密钥，双方派生出对称会话密钥，最后用对称加密传输 HTTP 数据。证书解决公钥信任问题，非对称加密解决密钥交换，对称加密解决性能，MAC/AEAD 解决完整性。TLS 1.3 用 ECDHE 实现前向安全，握手更快，HTTP/3 则基于 QUIC 内置 TLS 1.3。”
