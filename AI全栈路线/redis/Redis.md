# Redis

> 建议先看完 [MySQL](../数据库/MySQL.md)。Hello World 可以没有 Redis；等你碰到「同一页被狂刷、要限流、要验证码、两台机器抢同一件事」再请它。
>
> 和 MySQL 的分工只有一句：**真相在 MySQL，加速和短状态在 Redis。** 订单有没有支付，以 MySQL 为准。

---

## 是什么，能做什么

Redis 是一个把数据放在**内存**（电脑的运行内存，比磁盘快得多）里的小仓库。按一个 key（名字）读写，通常零点几毫秒。

不要把它理解成「更快的 MySQL」：

- 没有表，没有 `JOIN`，不能随口说「把姓李的用户和他们的订单拼起来」
- 默认崩溃可能丢掉最近几秒（即便开了落盘，也不该拿它当唯一账本）

更像一块**带格子的白板**：写得快、擦得也快，格子还能设置「5 分钟后自动擦掉」。

它真正强的是这四件事：

1. **同一份热数据被读几千次**：商品详情 JSON 不用每次都去问 MySQL
2. **原子计数**：两个请求同时 +1，用 `INCR` 不会都读到 7 再都写成 8
3. **带过期的短状态**：验证码、一分钟内登录几次，时间到了自己消失
4. **跨进程协调**：你开了好几个后端进程，大家抢同一把锁、认同一个「这请求已经处理过了」

| 能做 | 不要靠它做 |
|---|---|
| 热点读、计数、限流、短锁 | 用户、订单、库存的唯一真相 |
| 到点自动过期（TTL） | 多表关联、报表 |
| 排行榜、小队列 | 把 10GB 商品正文全塞进来当库 |

没有 Redis，单机、访问量不大、数据全走 MySQL，照样能跑。痛点出现在：**MySQL 被同一条详情打穿、并发下计数错、短状态没地方放、多实例抢同一资源。**

## 基础用法

### 连上

本机（Redis 装在你电脑上时）：

```bash
redis-cli -h 127.0.0.1 -p 6379
PING    # 通了会回 PONG
```

如果 Redis 跑在 Docker 里、你的接口也在 Docker 里，**容器内部**要用服务名，不要用 `localhost`：

```text
redis://redis:6379/0
```

`localhost` 在接口容器里指的是容器自己，连的不是旁边那个 Redis。这点 Docker 篇还会再说。

### Key 怎么起名

Redis 没有表，全靠 key 的名字区分。约定：

```text
业务:对象:id[:字段]

product:42:detail     商品 42 的详情缓存
login:ip:1.2.3.4      这个 IP 的登录次数
order:idem:req_abc    这张请求有没有处理过
lock:product:42       商品 42 的锁
```

不要起 `p42` 这种以后自己也看不懂的名字。按前缀删缓存、排查问题，全靠这个约定。

### 五类最常用的结构（先当五种盒子）

**String（一根绳子 / 一份完整 JSON）**：缓存、计数、锁，最常用。

```bash
SET product:42:detail '{"id":42,"name":"茅台","price":149900}' EX 300
GET product:42:detail
INCR login:ip:1.2.3.4      # 原子 +1
EXPIRE login:ip:1.2.3.4 60 # 60 秒后消失
DEL product:42:detail      # 删掉
```

`EX 300` 表示 300 秒后自动过期。验证码、限流窗口都靠这个，不必自己写定时删除。

**Hash（一张小卡片，上面有多个字段）**：改价格不必重写整份 JSON。

```bash
HSET product:42 name 茅台 price 149900 stock 10
HGET product:42 price
HINCRBY product:42 stock -1
```

**List（队列，先进或后进你自己定）**：适合「上传完 PDF，后台慢慢切片」。

```bash
LPUSH rag:parse 101   # 把任务 101 放进去
BRPOP rag:parse 5     # 后台来取，最多等 5 秒
```

**Set（一堆不重复的东西）**：用户点过哪些商品。

```bash
SADD user:7:viewed 42 43
SISMEMBER user:7:viewed 42
```

**ZSet（带分数的排行）**：分数可以是销量，也可以是「几点几分该执行」。

```bash
ZINCRBY product:sold 1 42          # 商品 42 销量 +1
ZREVRANGE product:sold 0 9 WITHSCORES   # 前 10 名
```

### 原子写：NX（不存在才写）

```bash
SET lock:product:42 worker-a NX EX 10
```

- `NX`：这个 key 还不存在，才写成功。抢锁、防重复下单都靠它。
- `EX 10`：10 秒后自动解开。进程挂了，锁也不会永远占着。

解锁不要直接 `DEL`：你的锁可能已经过期、别人已经抢到了，你这一 `DEL` 会把别人的锁删掉。正确做法是：先确认还是自己的值，再删。下面这段小脚本（Lua，Redis 能保证它一次执行完）就是这个意思：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

初学先记住结论：**抢锁用 SET NX EX，解锁要确认是自己的。**

## 常用场景

下面都假设：接口用 FastAPI（Python 写 HTTP 接口），数据在 MySQL。Redis 只出现在「MySQL 单独扛不住 / 不该扛」的位置。

**1. 商品详情缓存（旁路缓存，英文 Cache-Aside）**

详情接口每秒被打开几千次，MySQL 按 id 查再快也会排队。约定：

```text
读：先问 Redis GET product:{id}:detail
    有 → 直接返回
    没有 → 问 MySQL → 把结果 SET 进 Redis（带 EX 300）→ 返回

写：先 UPDATE MySQL
    成功后再 DEL product:{id}:detail   -- 删掉旧缓存
```

先改 MySQL 再删缓存，不要先改 Redis。缓存可以丢，库不能错。下一次有人读，会从 MySQL 再造一份。`EX 300` 当保险：万一删除失败，最多脏 5 分钟。

生成详情的模型跑完后：`UPDATE products SET content=?`，然后 `DEL` 对应缓存。

**2. 登录 / 接口限流**

同一 IP 一分钟只许登 10 次：

```text
n = INCR login:ip:{ip}     # 次数 +1
如果是第一次，再 EXPIRE 60 秒
n > 10 → 返回 429（请求太多）
```

验证码输错几次、生成详情接口防刷，同一套路。时间窗口用 TTL，不必自己扫过期数据。

**3. 验证码、谁还在听流**

```text
SET sms:13800138000 834921 EX 300   # 验证码 5 分钟
SET sse:user:7 1 EX 60              # 这个用户还在听打字机效果
```

SSE 可以先理解成：服务器把字一个一个推到网页上，像打字机。这类状态过期就该消失，放 MySQL 还要自己扫过期行。

**4. 同一请求不要下单两次（幂等）**

手机网络卡了，用户点了两次「支付」，前端可能带着同一个请求编号重试：

```text
SET order:idem:{key} 1 NX EX 86400
失败 → 已经处理过，把上次结果返回去
成功 → 走 MySQL 下单事务，结果也记在这个 key 里
```

库存扣得对不对，仍由 MySQL 事务负责。Redis 只挡住重复提交。

**5. 分布式锁：两台机器不要一起生成同一商品详情**

两台后端同时给商品 42 调大模型，会双倍花钱。

```text
SET lock:gen:42 {随机串} NX EX 30
抢到 → 调模型 → UPDATE MySQL → DEL 缓存 → 用 Lua 按随机串解锁
没抢到 → 等一下，或返回「正在生成」
```

锁只保证「不要同时做」，生成出来的详情仍写 MySQL。

**6. 上传队列和排行榜**

用户上传大 PDF：接口只在 MySQL 插入一条「待解析」，再 `LPUSH rag:parse {文档id}`。后台工人 `BRPOP` 取出来切片，最后回写 MySQL 状态。

热销榜：下单成功 `ZINCRBY product:sold 1 {商品id}`，列表页取前 10。销量对账仍可查订单表，ZSet 只是展示用。

**7. Pub/Sub 还是 Stream（先知道区别）**

| | Pub/Sub（广播） | Stream（小日志流） |
|---|---|---|
| 当时没人听 | 消息丢了 | 还在 |
| 适合 | 「解析完了，通知正在开着的页面」 | 必须处理的后台任务 |

网页上的打字机效果本身走 HTTP，不必经 Redis。只有「另一台机器上的工人解析完了，要通知这台接口去推」时，才用广播或 Stream。

## 不用 Redis 的痛点，以及怎么解决

**详情页把 MySQL 打满。** 同一 `WHERE id=?` 每秒几千次。旁路缓存：读 Redis，没有再读库；写库成功后删对应 key，带过期时间。

**缓存穿透：有人乱打不存在的 id。** 每次都打到 MySQL。对「查不到」也缓存很短一段时间（比如 30 秒），或先挡住非法 id。

**缓存击穿：一个特别热的 key 刚好过期，请求同时去打 MySQL。** 重建时加一把短锁，只让一个请求去查库，别人稍等再读 Redis。

**缓存雪崩：大批 key 同一秒过期。** 过期时间加一点随机，比如 300 秒再加 0～60 秒。不要所有商品都整点一起过期。

**两个请求把计数都加成了同一个值。** 应用里 `GET` 再 `SET` 不是一步完成的。改用 `INCR`。库存最终仍以 MySQL `UPDATE ... WHERE stock >= 1` 为准。

**验证码记在程序的一个字典里。** 你开几个进程就不共享；进程一重启全没。放到 Redis，带过期。

**两台接口同时跑同一件贵操作。** `SET key 随机串 NX EX` 抢锁，用 Lua 按随机串释放。不要 `DEL` 别人的锁。

**把订单只存在 Redis。** 重启、内存满、过期，订单没了。该持久的进 [MySQL](../数据库/MySQL.md)。

**缓存和库不一致。** 常见原因：先改了 Redis、MySQL 失败却没改回来；或先删缓存再写库，中间被读请求把旧值又灌回去。记住：先成功写 MySQL，再删缓存。

一条判断标准：这数据 **丢了能不能从 MySQL 再造出来**？能，才适合 Redis。不能，就不要只放 Redis。

## 常见面试题

**没有 Redis 不是也能跑吗？为什么还要它？**

能跑。访问量不大时不需要。它解决的是 MySQL 不该反复扛的事：详情被狂刷、多进程要共享验证码和限流、两台机器不要同时做同一件贵操作。判断：丢了能不能从 MySQL 再造？能，才放 Redis。

**旁路缓存怎么写？为什么是删缓存不是改缓存？**

读：先 Redis，没有再 MySQL，再写回 Redis。写：先成功写 MySQL，再删 Redis。改缓存容易出现「库失败了缓存却是新的」，或并发下把旧值写回去。删掉后下一次读会重建。

**穿透、击穿、雪崩有什么区别？**

| 问题 | 现象 | 怎么防 |
|---|---|---|
| 穿透 | 查根本不存在的 id，每次打到库 | 空结果也缓存很短；挡住乱 id |
| 击穿 | 一个热点刚好过期，大家一起回源 | 重建时加一把短锁，只让一个打库 |
| 雪崩 | 大批 key 同一秒过期 | 过期时间加随机抖动 |

**分布式锁怎么实现？为什么不能直接 DEL？**

`SET lock {随机串} NX EX`。解锁前确认还是自己的随机串再删。直接 `DEL` 可能删掉别人已经抢到的锁（你的锁到期后别人写入，你回来还 DEL）。

**为什么计数要用 INCR，不能 GET 再 SET？**

两步不是原子的，两个请求都读到 7，都写成 8，少加了一次。限流、错误次数用 `INCR`。库存最终仍以 MySQL 为准。

**Redis 为什么单线程还很快？能当数据库用吗？**

命令执行是单线程，但数据在内存里，大多数操作非常便宜，没有「解析 SQL + 翻磁盘」那套成本。持久化（定期快照 / 写日志）只是保险，仍可能丢最近一秒，所以订单真相不能只放 Redis。

**五种结构各举一个业务例子。**

String：详情 JSON、验证码、锁、限流。Hash：商品多个字段。List：解析队列。Set：点过哪些商品。ZSet：热销榜。
