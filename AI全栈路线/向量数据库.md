# pgvector 向量数据库教程

> 从零开始，一步步在 PostgreSQL 中使用 pgvector 进行向量数据的增删改查。

---

## 第 0 课：什么是向量数据库？

### 普通数据库 vs 向量数据库

普通数据库存的是结构化数据：

```
商品表 Product：
| id  | name    | brand  | price |
|-----|---------|--------|-------|
| 1   | 茅台    | 茅台   | 1499  |
| 2   | 五粮液  | 五粮液 | 899   |
```

你要查"茅台"，就用 `WHERE name = '茅台'`。但如果你问**"和茅台口感相似的酒有哪些"**，普通数据库答不了——它不理解"口感相似"是什么意思。

向量数据库多了一个 **embedding（嵌入向量）** 字段：

```
| id | name | brand  | price | embedding                          |
|----|------|--------|-------|-------------------------------------|
| 1  | 茅台 | 茅台   | 1499  | [0.12, -0.34, 0.56, ..., 0.78]     |
| 2  | 五粮液| 五粮液 | 899   | [0.11, -0.32, 0.55, ..., 0.77]    |
| 3  | 可乐  | 可口可乐| 5    | [-0.89, 0.12, -0.67, ..., 0.03]   |
```

### 什么是 embedding？

embedding 是一个**浮点数数组**（比如 1536 个数字），它是用 AI 模型把文本/图片"翻译"成的一串数字。关键特性：

```
"酱香型白酒，53度，贵州茅台"  →  [0.12, -0.34, 0.56, ...]  ← 向量A
"浓香型白酒，52度，四川五粮液" →  [0.11, -0.32, 0.55, ...]  ← 向量B（和A很接近）
"碳酸饮料，可乐味"            →  [-0.89, 0.12, -0.67, ...] ← 向量C（和A差很远）
```

**语义越相似的内容，向量之间的距离越近。** 向量数据库的核心能力就是：给一个查询向量，快速找到数据库里"距离最近"的几条记录。

### 为什么不直接比较？要用数据库？

- 10 万条数据暴力遍历算距离要几秒，太慢
- 向量数据库用**索引**（HNSW / IVF）把查找从 O(n) 降到近似 O(log n)，毫秒级返回

## 第 3 课：建表（Create Table）

```sql
CREATE TABLE wines_demo (
  id    SERIAL PRIMARY KEY,
  name  TEXT NOT NULL,
  taste TEXT NOT NULL,
  embedding vector(4)
);
```

| 部分 | 含义 |
|---|---|
| `CREATE TABLE wines_demo` | 创建一张名为 wines_demo 的教学表 |
| `id SERIAL PRIMARY KEY` | 自增整数主键（1, 2, 3...），每插一行自动 +1 |
| `name TEXT NOT NULL` | 酒名，文本类型，不允许为空 |
| `taste TEXT NOT NULL` | 口味描述，文本类型，不允许为空 |
| `embedding vector(4)` | **向量字段**，4 维（教学用，真实场景用 768 或 1536 维） |

### 知识点：`vector(4)` 是什么？

这是 pgvector 提供的自定义类型，表示"一个有 4 个浮点数的数组"。存储格式是 `[0.1, 0.2, 0.3, 0.4]` 这样的字符串。

真实场景中维度由你选择的 AI 模型决定：

| AI 模型 | 维度 |
|---|---|
| OpenAI `text-embedding-3-small` | `vector(1536)` |
| OpenAI `text-embedding-3-large` | `vector(3072)` |
| 本地 `bge-m3` | `vector(1024)` |
| 本地 `nomic-embed-text` | `vector(768)` |

### 执行后效果

```
CREATE TABLE
```

## 第 6 课：向量查询（Read）—— 核心能力

### 场景

用户搜索"酱香白酒"，AI 模型把它转换成了向量 `[0.88, 0.12, 0.82, 0.18]`。现在要在数据库里找到和这个向量最相似的酒。

```sql
SELECT
  id,
  name,
  embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector  AS distance,
  1 - (embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector) AS similarity
FROM wines_demo
ORDER BY embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector
LIMIT 3;
```

### 逐行解释

```sql
SELECT
  id, name,                                                          -- 查出 id 和酒名

  -- ↓ 关键运算符：<=>  （余弦距离）
  embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector  AS distance,

  -- ↓ 相似度 = 1 - 距离（方便人类理解）
  1 - (embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector) AS similarity

FROM wines_demo                                                     -- 从表里查

-- ↓ 按距离从小到大排序（越小 = 越相似）
ORDER BY embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector

LIMIT 3;                                                            -- 只取前 3 条
```

### 知识点

| 概念 | 含义 |
|---|---|
| `<=>` | pgvector 的**余弦距离**运算符，衡量两个向量的"方向差异" |
| `distance` | 两个向量的距离值。**0 = 完全相同，1 = 无关，2 = 完全相反** |
| `similarity` | 相似度 = 1 - 距离。**1 = 完全相同，0 = 无关** |
| `::vector` | 类型转换，把字符串 `'[0.88, ...]'` 转成 vector 类型 |
| `ORDER BY ... <=>` | 按距离排序，最相似的排在最前面 |
| `LIMIT 3` | 只返回最相似的 3 条（Top-K 查询） |

### 执行后效果

```
 id |  name  |       distance        |     similarity
----+--------+-----------------------+--------------------
  1 | 茅台   | 0.0005321586932111044 | 0.9994678413067889
  2 | 五粮液 | 0.0031217441942016366 | 0.9968782558057984
  5 | 江小白 | 0.45080507589701735   | 0.5491949241029827
(3 rows)
```

### 结果解读

```
茅台    distance=0.0005 → 几乎一模一样 ✅（都是酱香高度酒，相似度 99.9%）
五粮液  distance=0.003  → 非常相似     ✅（浓香但也是高度白酒，相似度 99.7%）
江小白  distance=0.45   → 有点关系     😐（都是白酒但风格不同，相似度 54.9%）
可乐    没进前3 → 差太远了              ❌（被 LIMIT 3 淘汰了）
```

## 第 7 课：三种距离运算符对比

pgvector 提供了三种距离运算符，适用不同场景：

```sql
SELECT
  name,
  embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector  AS cosine_dist,
  embedding <-> '[0.88, 0.12, 0.82, 0.18]'::vector  AS euclidean_dist,
  embedding <#> '[0.88, 0.12, 0.82, 0.18]'::vector  AS neg_inner_product
FROM wines_demo
ORDER BY cosine_dist;
```

### 三种运算符

| 运算符 | 名称 | 计算方式 | 值域 | 越小越 |
|---|---|---|---|---|
| `<=>` | 余弦距离 | 比较两个向量的"方向"差异，不看大小 | 0~2 | 越相似 |
| `<->` | 欧几里得距离 | 两点之间的直线距离（勾股定理） | 0~∞ | 越相似 |
| `<#>` | 负内积 | 同时看方向和大小 | -∞~0 | 越相似 |

### 执行后效果

```
  name  |      cosine_dist      |   euclidean_dist    |  neg_inner_product
--------+-----------------------+---------------------+----------------------
 茅台   | 0.0005321586932111044 | 0.03999997766687843 |  -1.496000051498413
 五粮液 | 0.0031217441942016366 | 0.10770328248716833 |  -1.4260001182556152
 江小白 | 0.45080507589701735   | 1.1007270079461273  |  -0.7259999513626099
 汾酒   | 0.5218089687567433    | 1.2006664670488303  |  -0.656000018119812
 可乐   | 0.7458158516495113    | 1.5500321969410684  |  -0.40799999237060547
(5 rows)
```

### 什么时候用哪种？

| 场景 | 推荐运算符 | 原因 |
|---|---|---|
| **文本语义搜索** | `<=>` 余弦 | 文本变长后向量绝对值变大，但方向不变。余弦只比方向不受长度影响 |
| **图片相似度** | `<->` 欧几里得 | 图片向量通常已归一化，直接比绝对距离更直观 |
| **推荐系统** | `<#>` 内积 | 需要考虑向量的"强度"（如用户偏好程度） |

## 第 8 课：更新向量数据（Update）

### 场景

假设茅台换了新的 AI 模型来生成 embedding，需要更新向量：

```sql
UPDATE wines_demo
SET embedding = '[0.92, 0.08, 0.85, 0.15]'::vector
WHERE name = '茅台';

SELECT name, embedding FROM wines_demo WHERE name = '茅台';
```

### 命令解释

| 部分 | 含义 |
|---|---|
| `UPDATE ... SET` | 标准的 SQL 更新语法 |
| `'...'::vector` | 类型转换，把字符串转成 vector 类型（和插入时一样） |
| `WHERE name = '茅台'` | 限定条件，只改茅台这一行。**不加 WHERE 会改全表** |

### 执行后效果

```
UPDATE 1
  name |       embedding
------+-----------------------
 茅台 | [0.92,0.08,0.85,0.15]
(1 row)
```

`UPDATE 1` 表示成功更新了 1 行。向量已从 `[0.9,0.1,0.8,0.2]` 变成了 `[0.92,0.08,0.85,0.15]`。

> 真实场景中，embedding 通常由后端代码调用 AI 模型 API 生成后写入，不会手动填。

## 第 10 课：索引加速（性能关键）

### 先查看当前索引

```sql
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'wines_demo';
```

| 部分 | 含义 |
|---|---|
| `pg_indexes` | PostgreSQL 的系统表，记录所有索引信息 |
| `WHERE tablename = 'wines_demo'` | 只看 wines_demo 表上的索引 |

### 执行后效果

```
    indexname    |                                 indexdef
-----------------+---------------------------------------------------------------------------
 wines_demo_pkey | CREATE UNIQUE INDEX wines_demo_pkey ON public.wines_demo USING btree (id)
(1 row)
```

只有主键的 btree 索引，没有向量索引。

### 知识点：为什么需要向量索引？

```
没有索引（全表扫描）：
  遍历每一行 → 算距离 → 排序 → 返回
  10 万条数据 = 算 10 万次 → 慢

有索引（HNSW 图结构）：
  从入口节点出发 → 沿着"近邻边"跳跃 → 快速定位到相似区域 → 返回
  10 万条数据 ≈ 算几百次 → 毫秒级
```

### 创建 HNSW 向量索引

```sql
CREATE INDEX idx_wines_embedding ON wines_demo
  USING hnsw (embedding vector_cosine_ops);
```

| 部分 | 含义 |
|---|---|
| `CREATE INDEX idx_wines_embedding` | 创建一个名为 idx_wines_embedding 的索引 |
| `USING hnsw` | 使用 HNSW 算法（Hierarchical Navigable Small World，分层导航小世界图） |
| `embedding` | 对哪个字段建索引 |
| `vector_cosine_ops` | 指定用余弦距离 `<=>` 做索引 |

### 知识点：两种向量索引

| 索引类型 | 特点 | 适合场景 |
|---|---|---|
| **HNSW** | 图结构，分层导航，查询快，构建稍慢 | < 100 万向量（推荐） |
| **IVFFlat** | 聚类分区，构建快，需调参 | > 100 万向量 |

### 知识点：ops 必须和查询运算符一致

| 查询运算符 | 建索引时用的 ops |
|---|---|
| `<=>` 余弦距离 | `vector_cosine_ops` |
| `<->` 欧几里得距离 | `vector_l2_ops` |
| `<#>` 内积 | `vector_ip_ops` |

> **如果 ops 和查询运算符不一致，索引不会生效，会退化成全表扫描。**

### 执行后效果

```
CREATE INDEX
```

## 第 11 课：带过滤条件的混合查询

### 场景

用户搜索"酱香"，但只要价格 500 元以上的酒。需要 SQL 过滤 + 向量排序写在一条语句里。

### 先加价格字段

```sql
ALTER TABLE wines_demo ADD COLUMN price INT DEFAULT 0;
UPDATE wines_demo SET price = 1499 WHERE name = '茅台';
UPDATE wines_demo SET price = 899  WHERE name = '五粮液';
UPDATE wines_demo SET price = 499  WHERE name = '汾酒';
UPDATE wines_demo SET price = 99   WHERE name = '江小白';
```

| 语句 | 含义 |
|---|---|
| `ALTER TABLE ... ADD COLUMN price INT` | 给表加一个 price 字段，整数类型，默认值 0 |
| `UPDATE ... SET price = 1499 WHERE name = '茅台'` | 把茅台的价格设为 1499 |

### 执行混合查询

```sql
SELECT
  name,
  price,
  1 - (embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector) AS similarity
FROM wines_demo
WHERE price >= 500
ORDER BY embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector
LIMIT 5;
```

### 逐行解释

```sql
SELECT
  name, price,                                                    -- 查出酒名和价格
  1 - (embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector) AS similarity  -- 算相似度

FROM wines_demo
WHERE price >= 500                                                 -- ① 先过滤：只要 500 元以上的
ORDER BY embedding <=> '[0.88, 0.12, 0.82, 0.18]'::vector          -- ② 再按向量相似度排序
LIMIT 5;                                                           -- ③ 最多返回 5 条
```

### 知识点：混合查询

`WHERE price >= 500` 是普通 SQL 过滤，`ORDER BY embedding <=>` 是向量排序。pgvector 支持把它们写在一条 SQL 里。

```
执行顺序：
  ① WHERE 过滤掉不符合条件的行（江小白 99 元、汾酒 499 元被淘汰）
  ② 对剩下的行做向量排序（茅台、五粮液）
  ③ LIMIT 返回前 5 条
```

### 执行后效果

```
  name  | price |     similarity
--------+-------+--------------------
 茅台   |  1499 | 0.9989502374500131
 五粮液 |   899 | 0.9968782558057984
(2 rows)
```

江小白（99 元）和汾酒（499 元）被价格条件过滤掉了，只剩茅台和五粮液。

```
│                                                                 │
│  ③ 查询   SELECT ... ORDER BY embedding <=> query LIMIT K       │
│     <=> = 余弦距离，越小越相似                                    │
│                                                                 │
│  ④ 更新   UPDATE ... SET embedding = '[...]'::vector            │
│     换了 AI 模型或内容修改后需要更新                                │
│                                                                 │
│  ⑤ 删除   DELETE FROM ... WHERE ...                             │
│     和普通 SQL 一样                                               │
│                                                                 │
│  ⑥ 索引   CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)│
│     数据量 > 1000 条时必须加，否则全表扫描很慢                      │
│                                                                 │
│  ⑦ 混合   WHERE 条件 + ORDER BY 向量距离                         │
│     SQL 过滤 + 向量排序，一条 SQL 搞定                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 核心概念速查

| 概念 | 一句话解释 |
|---|---|
| **embedding** | AI 模型把文本/图片转换成的浮点数数组，语义相似 → 向量相似 |
| **维度** | 数组长度（如 1536），由 AI 模型决定，不可随意改 |
| **`<=>` 余弦距离** | 比较两个向量的"方向"差异，0=完全相同，不看长度 |
| **相似度** | `1 - 余弦距离`，1=完全相同，越接近 1 越相似 |
| **HNSW 索引** | 图结构索引，让查找从"逐个比较"变成"跳着找"，快 1000 倍 |
| **ops** | 索引和查询用的距离运算符必须一致（cosine/l2/ip 三选一） |
| **混合查询** | `WHERE` 普通过滤 + `ORDER BY` 向量排序，写在一条 SQL 里 |
