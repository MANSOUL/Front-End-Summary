以 PostgreSQL 使用的 paradeDB 提供的 pg_search 提供的扩展为例；

建索引时 ParadeDB 在后台完成分词（`chinese_compatible` 中文分词器）、倒排表构建、IDF 统计——这些都是扩展内部实现，没有对应的应用代码。

```sql
CREATE INDEX products_bm25_idx ON products

USING bm25 (id, embedded_text)

WITH (key_field = 'id', text_fields = '{"embedded_text": {"tokenizer": {"type": "chinese_compatible"}}}');
```

BM25的几个关键概念：分词、倒排表、IDF（逆文档频率）、RRF（倒数排名融合，丢掉原始分，只加名次，不加分数）【和向量检索一起使用】

这三个概念正好串起一条链：倒排表解决"怎么快速找到含某个词的文档"，IDF 解决"找到之后谁更重要"，RRF 解决"两路检索结果怎么合成一个榜"。我用三张图讲清楚，全部用你项目里的真实数据举例。

第一张：倒排表。普通表是"文档 → 词"（每张产品卡存一段文本），查"酱香"就得扫 225 行逐字匹配。倒排表把它反过来存——"词 → 含这个词的文档列表"（叫 posting list）。建索引时 ParadeDB 对每张卡的 `embedded_text` 分词，为每个词记下它出现在哪些卡里。查询时只要按词取回那一行列表，不用扫任何一张卡：

第二张：IDF。光找到还不够——命中的卡有几十张，谁排前面？BM25 的核心直觉是：**越稀有的词越有区分度**。"口感"出现在 180 张卡里，命中它说明不了什么；"阿玛罗尼"只在 1 张卡里出现，命中它几乎就是答案本身。IDF（逆文档频率）把这个直觉量化成权重：

第三张：RRF（倒数排名融合）。你的检索是两路并行——BM25 路返回按 BM25 分排序的榜，向量路返回按余弦距离排序的榜。麻烦在于：这两个原始分数**量纲完全不同**（BM25 是 0~10+ 的分值，余弦距离是 0~1），不能直接相加。RRF 的解法很巧妙：**扔掉原始分，只看名次**——每个文档得 `1/(60+名次)` 分，两路各自累计后相加。这就是为什么是 `1 / (RRF_K + i + 1)`（`i` 从 0 起，所以 `i+1` 就是名次）：

串起来的完整链路：

1. **倒排表**（建索引时）：`chinese_compatible` 分词器把 `embedded_text` 拆成词，建立 词→产品ID 的映射 —— 这是 `@@@` 操作符能毫秒级返回的原因
2. **IDF + 词频**（查询时）：`paradedb.score(id)` 对每个命中卡按"命中词的稀有度 × 出现次数"算出 BM25 分 —— 这就是 BM25 路排序的依据
3. **RRF**（融合时）：BM25 榜和向量榜各取 top10，按 `1/(60+名次)` 累计 —— 解决两路分数不可比的问题，且天然奖励"双路命中"

几个工程上值得知道的点：

- **k=60 是经验值**（来自原论文 Cormack et al. 2009），作用是让 #1 和 #10 的差距不至于悬殊（1/61 vs 1/70，只差 15%），避免单一路的第 1 名霸榜
- **RRF 不需要归一化**，这是它相比"加权求和分数"的最大优势——BM25 分数会随语料库变化漂移，向量距离分布也随模型变，名次却永远稳定
- **降级路径**：嵌入 API 挂掉时向量路返回空，RRF 自动退化成只用 BM25 榜，公式照样成立——这是 try/catch 兜底的意义
