# SQL 索引

> 目标：看懂为什么有的 SQL 很快、有的会扫全表，以及什么时候该建索引、什么时候建了也没用。

默认按 **PostgreSQL** 讲（和仓库里的 pgvector 笔记一致）。面试里常考的 MySQL InnoDB 差异会单独标出来。

---

## 第 0 课：索引是什么

表是一堆行。没有索引时，数据库要找 `email = 'bob@x.com'`，只能从头到尾扫一遍，这叫 **Seq Scan（全表扫描）**。

索引是另一份按某个键排好序的目录。目录项不存整行，只存：

```
键值 → 这一行在表里的位置
```

PostgreSQL 里这个位置叫 `ctid`（页号 + 行号）。查到键之后，再拿 `ctid` 回表取整行。

可以把它想成通讯录：

| 没有索引 | 有 email 索引 |
|---|---|
| 翻完整本通讯录，看每一页的邮箱 | 先按字母翻到 B，再拿页码去对应那一页 |

```sql
CREATE TABLE users (
  id         BIGSERIAL PRIMARY KEY,
  email      TEXT NOT NULL,
  name       TEXT NOT NULL,
  status     TEXT NOT NULL,          -- active / banned
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX idx_users_email ON users (email);
CREATE INDEX idx_users_status_created ON users (status, created_at);
```

`PRIMARY KEY` 本身就会带一个唯一索引。上面又额外建了两个：email 唯一索引，以及 `(status, created_at)` 联合索引。

## 第 1 课：B-Tree 长什么样

PostgreSQL / MySQL 默认索引都是 **B-Tree**（准确说是 B+Tree 这一族：数据在叶子，内部节点只做路标）。

假设 email 索引里有 5 个键：

```
              [ cara@x.com ]
             /              \
 [ alice@   bob@ ]     [ cara@   dan@   eve@ ]
     ↓        ↓            ↓       ↓       ↓
   行位置   行位置        行位置   行位置   行位置
```

查 `WHERE email = 'bob@x.com'` 的路径：

1. 根节点：`bob@` < `cara@`，走左边
2. 叶子里二分找到 `bob@`
3. 用叶子上的 `ctid` 回表取整行

复杂度接近 `O(log N)`。100 万行大概只要十几次比较；全表扫描是 `O(N)`，要看 100 万次。

叶子节点是有序且互相串起来的，所以范围查询也能走索引：

```sql
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'
```

## 第 2 课：回表，以及覆盖索引

索引叶子上通常只有「键 + 行位置」，没有 `name`、`status` 这些列。

```sql
SELECT name FROM users WHERE email = 'bob@x.com';
```

执行器会：

1. 用 `idx_users_email` 找到 `bob@x.com` 的 `ctid`
2. **回表**：再去堆表（heap）里把那一行读出来
3. 取出 `name`

如果查询需要的列，索引里全都有，就不用回表，这叫 **Index Only Scan（覆盖索引）**：

```sql
-- email 索引只覆盖 email，还是要回表拿 name
SELECT name  FROM users WHERE email = 'bob@x.com';

-- 只查 email，索引里已经有了
SELECT email FROM users WHERE email = 'bob@x.com';
```

想让「按邮箱查姓名」也不回表，可以把姓名也放进索引：

```sql
CREATE INDEX idx_users_email_name ON users (email) INCLUDE (name);
```

`INCLUDE` 是 PostgreSQL 的 covering index 写法：`name` 不参与排序，只跟在叶子上当载荷。

> MySQL InnoDB 差异：InnoDB 的主键是 **聚簇索引**，整行就躺在主键叶子里。二级索引叶子存的不是 `ctid`，而是主键值。所以 InnoDB 回表 = 拿主键再查一次聚簇索引。PostgreSQL 没有这种聚簇主键，所有普通索引地位类似，行主体在 heap 里。

## 第 3 课：联合索引和最左前缀

`idx_users_status_created (status, created_at)` 可以理解成：先按 status 排序，status 相同再按 created_at 排序。

一本先按「城市」再按「姓名」排的通讯录：

| 能用上 | 用不了 / 只能用一部分 |
|---|---|
| `WHERE status = 'active'` | `WHERE created_at > '2026-01-01'`（跳过了左边的 status） |
| `WHERE status = 'active' AND created_at > '2026-01-01'` | `WHERE created_at > '2026-01-01' AND status = 'active'` 仍然可以，优化器会调整 |
| `WHERE status IN ('active','banned')` | `WHERE name = '李四'`（这个索引里没有 name） |

这就是 **最左前缀**：联合索引 `(a, b, c)` 对 `a`、`a+b`、`a+b+c` 有效；对只有 `b` 或只有 `c` 通常无效。

范围查询会截断后面的列：

```sql
-- status 等值，created_at 范围：两列都能用
WHERE status = 'active' AND created_at > '2026-01-01'

-- 如果索引是 (created_at, status)
-- created_at 已经是范围，后面的 status 很难再继续用这个索引做精确过滤
WHERE created_at > '2026-01-01' AND status = 'active'
```

经验：等值字段放左边，范围字段放右边。

## 第 4 课：索引失效的常见写法

有索引不等于会走索引。下面这些会让优化器放弃 B-Tree：

```sql
-- 1. 对索引列做函数 / 运算
WHERE lower(email) = 'bob@x.com'
WHERE created_at::date = '2026-01-01'

-- 2. 前导模糊
WHERE email LIKE '%bob%'      -- 不能用 B-Tree
WHERE email LIKE 'bob%'       -- 可以用，相当于范围

-- 3. 隐式类型转换（看起来无害，实际很常见）
-- 假设 phone 是 TEXT，你却拿数字去比
WHERE phone = 13800138000

-- 4. 对索引列用否定、两端都未知的 OR
WHERE status <> 'banned'
WHERE email = 'a' OR name = '李四'   -- 后半段没索引时，可能退化成全表

-- 5. 选择性太差
WHERE status = 'active'       -- 如果 99% 都是 active，全表扫描可能更快
```

对应修法：

```sql
-- 函数查询：建表达式索引
CREATE INDEX idx_users_email_lower ON users (lower(email));
WHERE lower(email) = 'bob@x.com'

-- 按天查时间：不要把列转成 date，改成范围
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
```

## 第 5 课：用 EXPLAIN 看有没有走索引

```sql
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'bob@x.com';
```

关键看 `EXPLAIN` 第一列的扫描类型：

| 扫描类型 | 含义 |
|---|---|
| `Seq Scan` | 全表扫描，没走索引，或优化器觉得扫表更便宜 |
| `Index Scan` | 走了索引，然后回表 |
| `Index Only Scan` | 覆盖索引，没回表 |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | 命中很多行时，先在索引里收集一批位置，再按页回表 |

还要看：

- `rows`：优化器估计命中多少行。估错了，计划就容易选错
- `actual time`：真正花了多少毫秒
- `Buffers`（加 `EXPLAIN (ANALYZE, BUFFERS)`）：读了多少页

`SELECT *` 很难覆盖索引，因为要所有列。生产里能写列名就写列名。

## 第 6 课：该不该建

索引不是免费的：

- 每条 `INSERT` / `UPDATE` / `DELETE` 都要维护索引
- 占磁盘
- 太多索引会让优化器更难选计划

值得建的情况：

1. `WHERE` / `JOIN` / `ORDER BY` 经常用到的列
2. 选择性好（值比较散），比如 email、订单号
3. 外键列（PostgreSQL **不会**自动给外键建索引，MySQL InnoDB 会）

不值得建：

1. 很小的表
2. 几乎只有两个值、而且分布极偏的列（比如 99% 都是 `active`）
3. 写多读少、又很少按它过滤的列

一条实用规则：**先写查询，用慢查询 / `EXPLAIN` 证明它慢，再针对性加索引。** 不要按表结构预先撒一把。

## 第 7 课：和事务的关系

索引不只决定快慢，也影响锁的粒度。

```sql
UPDATE users SET status = 'banned' WHERE email = 'bob@x.com';
```

- 有 email 唯一索引：先精确找到这一行，再锁这一行
- 没有索引：可能先扫很多行，锁的范围更大，并发更容易撞车

事务那篇会接着讲：隔离级别、行锁、以及 PostgreSQL 的 MVCC 为什么「读不阻塞写」。

## 速查

| 记住这句 | 含义 |
|---|---|
| 索引是排好序的目录，不是表本身 | 查完目录往往还要回表 |
| 默认是 B-Tree | 等值、前缀、范围都适合；两端模糊不适合 |
| 联合索引看最左前缀 | `(a,b)` 救不了「只查 b」 |
| 列上套函数 = 不用这个索引 | 要就建表达式索引 |
| `EXPLAIN` 里出现 `Seq Scan` | 先问：是不是没索引、失效了，还是命中行太多 |
| 索引加速读、拖慢写 | 按真实查询加，不按想象加 |
