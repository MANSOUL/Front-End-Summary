# 索引

> 建议先看完 [MySQL](../MySQL.md)。这篇只回答一件事：数据多了，怎样让常见查询不必一行行翻完整张表。

---

## 是什么，能做什么

没有索引时，`WHERE email = 'bob@x.com'` 只能从第一行比到最后一行。这叫**全表扫描**，表有 100 万行就比 100 万次。

**索引**是另一份按某列排好序的目录。像纸质字典前面的拼音目录：先在目录里找到「茅」，再翻到那一页。不必从第一页翻到最后一页。

InnoDB 里，主键比较特殊，它就是**聚簇索引**：目录的最底层直接放着整行数据。所以 `WHERE id=42` 最快，找到了就拿到整行，不用再翻一次。

普通索引（也叫二级索引）底层只放「这一列的值 + 主键 id」。按邮箱查时分两步：

1. 在 email 这份目录里找到对应的 id
2. **回表**：拿着这个 id，再去主键那份目录里取整行

如果查询只要的列，二级索引里已经都有了，就不用回表。这叫**覆盖索引**。

| 能做                      | 不能指望它做                 |
| ----------------------- | ---------------------- |
| 让「按邮箱查」「按状态列表」变快        | 让写入也变快（写入还要同时改目录）      |
| 顺便实现「这一列不能重复」（`UNIQUE`） | 挽救 `SELECT *` 去扫一张很大的表 |
| 缩小锁的范围（事务篇会碰到）          | 一列几乎都是同一个值时，仍可能不走索引    |

## 基础用法

```sql
CREATE TABLE users (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  email      VARCHAR(190) NOT NULL,
  status     VARCHAR(16) NOT NULL,
  created_at DATETIME NOT NULL,
  UNIQUE KEY uk_email (email),                 -- 唯一索引：邮箱不能重复，按邮箱查也快
  KEY idx_status_created (status, created_at)  -- 联合索引：两列合订成一本目录
);

-- 表已经存在时再补一个
ALTER TABLE users ADD KEY idx_status (status);

-- 看看现在有哪些索引
SHOW INDEX FROM users;

-- 问 MySQL：这条查询打算怎么走
EXPLAIN SELECT * FROM users WHERE email = 'bob@x.com';
```

`EXPLAIN` 先看这几列，其他列暂时不用记：

| 列       | 人话                                                                            |
| ------- | ----------------------------------------------------------------------------- |
| `type`  | `ALL` 全表一行行翻；`index` 把整本目录翻完；`range` 按范围；`ref` 用了非唯一索引等值；`const` 主键或唯一列等值（最快） |
| `key`   | 实际用了哪个索引。`NULL` 就是没用                                                          |
| `rows`  | 它估计要翻多少行                                                                      |
| `Extra` | `Using index` 覆盖索引，不用回表；`Using filesort` 没能靠索引排序，要额外排一次                       |

### 联合索引和最左前缀

`(status, created_at)` 可以想成：先按状态排序，状态相同的再按时间排。一本合订目录，必须从左边开始用。

| SQL                                                 | 能不能用这个索引            |
| --------------------------------------------------- | ------------------- |
| `WHERE status = 'on'`                               | 能，只用了左边             |
| `WHERE status = 'on' AND created_at > '2026-01-01'` | 能，两列都用              |
| `WHERE created_at > '2026-01-01'`                   | 通常不能（跳过了左边的 status） |
| `WHERE status = 'on' ORDER BY created_at`           | 能，连排序都省了            |

记法：等值（`=`）的列放左边，范围（`>`、`<`、`BETWEEN`）的列放右边。

范围会截断后面的列：索引是 `(a, b, c)`，条件写成 `a=? AND b>? AND c=?` 时，`c` 往往用不上，因为 `b` 已经是一段范围，后面不再有序。

### 什么写法会让索引失效（等于没建）

```sql
-- 1. 在列上套函数。改成范围比较
WHERE DATE(created_at) = '2026-01-01'
-- 改成：
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'

-- 2. 前导模糊。% 在开头，目录派不上用场
WHERE name LIKE '%茅台%'     -- 不能用 B 树索引
WHERE name LIKE '茅台%'      -- 可以用

-- 3. 类型不一致：phone 是字符串，却拿数字去比，MySQL 要转换，索引废了
WHERE phone = 13800138000
-- 改成：
WHERE phone = '13800138000'

-- 4. 否定、或 OR 另一边没有索引
WHERE status <> 'off'
WHERE email = 'a' OR name = '李四'
```

## 常用场景

| 你的查询                                 | 怎么建                          |
| ------------------------------------ | ---------------------------- |
| 登录 `WHERE email=?`                   | `UNIQUE(email)`，防重复 + 加速一起有  |
| 列表 `WHERE status=? ORDER BY id DESC` | 联合索引 `(status, id)`          |
| 某用户的订单 `WHERE user_id=?`             | `KEY(user_id)`               |
| 订单上的 `product_id`                    | 自己建；当外键时 InnoDB 通常也会带索引      |
| 只想知道 email 在不在                       | 唯一索引里已经有 email，不必 `SELECT *` |

商品详情 `WHERE id=?` 走主键，一般不用再加索引。

覆盖索引的样子：

```sql
-- 索引是 (status, created_at)，查询只要这两列
SELECT status, created_at FROM users WHERE status = 'on';
-- EXPLAIN 的 Extra 里希望看到 Using index
```

`SELECT *` 很难覆盖，因为要所有列，目录里放不下整行（主键除外）。

## 不用索引的痛点，以及怎么解决

**数据到十万、百万，列表从几毫秒变成几秒。** `EXPLAIN` 里 `type=ALL`。按**最慢的那条 SQL** 的 `WHERE` / `ORDER BY` 去建，不要按表结构先给每列撒一把。

**明明建了，还是全表扫。** 先看是不是上面那些失效写法。再看区分度：`status` 99% 都是 `on`，优化器可能觉得「反正几乎全要，不如直接扫表」。

**写入变慢、磁盘变大。** 每插入、修改、删除一行，所有相关目录都要改。用不上的删掉：`ALTER TABLE users DROP INDEX idx_xxx`。

**`SELECT ... FOR UPDATE WHERE email=?` 锁了一大片。** 没走索引时，数据库不知道锁哪几行，可能锁很多行。锁行的 `WHERE` 必须能用上主键或唯一索引，见 [事务](../事务/事务.md)。

**JOIN 慢。** 被拼上来的那张表，连接列要有索引。`orders.user_id`、`orders.product_id` 是第一批该建的。

一条实用规则：先把查询写对，慢了再 `EXPLAIN`，再针对性加。几百行的小表，加不加都无所谓。

## 常见面试题

**什么是聚簇索引？和普通索引有什么区别？**

主键就是聚簇索引，最底层是整行数据，按 id 查最快。普通索引最底层只有「列值 + 主键 id」，查完往往还要回表拿整行。所以主键要短、要稳，普通索引才会小。

**回表？覆盖索引？**

回表：普通索引找到 id 后，再去主键树读行。覆盖：你要的列目录里都有，不用回表。`EXPLAIN` 里出现 `Using index`。`SELECT *` 很难覆盖。

**最左前缀是什么？**

联合索引必须从左边第一列开始用。`(status, created_at)` 可以只查 status，不能只查 created_at。等值列放左，范围列放右。

**建了为什么不走？**

列上套了函数、字符串列拿数字比、`LIKE '%xx'`、`OR` 另一边没索引、或者这列区分度太差。用 `EXPLAIN` 看 `key` 是不是 `NULL`。

**索引是不是越多越好？**

不是。写数据时每本目录都要改。按最慢的 SQL 建，用不上的删。

**`EXPLAIN` 你先看哪几列？**

`type`（是不是 `ALL`）、`key`（用了哪个）、`rows`（估多少行）、`Extra`（有没有 `Using index` / `Using filesort`）。

**锁一行的 SQL，为什么可能锁一大片？**

`WHERE` 没走索引，数据库不知道锁谁。条件必须能用上主键或唯一索引。见 [事务](../事务/事务.md)。
