# 事务

> 建议先看 [MySQL](../MySQL.md)。索引篇能看更好：锁哪几行，经常取决于有没有索引。
>
> 这篇只回答一件事：好几句 SQL 怎样绑成「要么全留下，要么全回去」。

---

## 是什么，能做什么

想象你在 ATM 转账：A 账户少 100，B 账户多 100。如果只做成第一步、第二步断电了，100 块就蒸发了。

**事务**就是把多句 SQL 绑成一步。中间状态不能被别人当成最终结果。

网站里最典型的是下单：写一条订单、商品库存减 1。只成功一步，货和钱就对不上。

面试会问四个字母 **ACID**，用下单翻译成人话：

| 字母 | 人话 | 下单时 |
|---|---|---|
| A 原子性 | 绑在一起的几步，成功就全成功，失败就全撤销 | 订单和库存必须一起成或一起败 |
| C 一致性 | 规则始终成立 | 提交后库存不能是负数 |
| I 隔离性 | 别人看不到你还没做完的中间态 | 看不到「订单有了、库存还没扣」 |
| D 持久性 | 说保存成功了，断电也不丢 | `COMMIT` 返回后再崩溃，这单还在 |

四个里日常最容易踩的是**隔离**：两个请求同时来，彼此能看见什么。

MySQL 默认隔离级别叫 `REPEATABLE READ`（可重复读）。普通 `SELECT` 看到的是「我这单事务开始时」的快照，一般不会堵住别人写；`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 才会真的把行锁住。

## 基础用法

```sql
START TRANSACTION;   -- 开始：后面几句先不算最终结果

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;      -- 提交：两步都成功，真正落盘
-- ROLLBACK; -- 回滚：任何一步失败，两边都当没发生过
```

默认情况下，你每执行一句 SQL，MySQL 就自动提交（autocommit）。所以「改一句价格」不必自己开事务。只有**多步必须一起成功**时，才写 `START TRANSACTION`。

### 隔离级别（先混个脸熟）

两个窗口同时办业务，能看见对方到哪一步，由隔离级别决定。

| 级别 | 脏读 | 不可重复读 | 幻读 | 什么时候用 |
|---|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 基本不用 |
| READ COMMITTED | 不会 | 可能 | 可能 | 希望每句 SQL 都看到别人刚提交的最新值 |
| REPEATABLE READ | 不会 | 不会 | InnoDB 下大多能防 | **MySQL 默认，先用这个** |
| SERIALIZABLE | 不会 | 不会 | 不会 | 冲突特别多、宁可排队 |

三个词用人话：

- **脏读**：读到别人还没按保存的修改（对方可能马上撤销）。
- **不可重复读**：你这单事务里读同一行两次，中间被别人改了，两次结果不一样。
- **幻读**：你这单事务里按同一条件查两次，行数变了（别人插入或删除了）。

现在先记住：默认 RR 就够用。真要改，这样写：

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
-- ...
COMMIT;
```

### 哪些语句会真的锁行

```sql
SELECT stock FROM products WHERE id = 42 FOR UPDATE;   -- 锁住这行，别人改不了，直到你提交
UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock >= 1;
DELETE FROM products WHERE id = 42;
```

`WHERE` 必须能用上索引（最好是主键或唯一索引），否则数据库不知道锁哪几行，可能锁很大一片。这就是为什么事务和索引要一起看。

## 常用场景

**下单扣库存。** 事务要短，库存让数据库自己判断：

```sql
START TRANSACTION;

INSERT INTO orders (user_id, product_id, amount, status)
VALUES (7, 42, 1, 'created');

UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock >= 1;

-- 应用里看 UPDATE 影响了几行：是 0 就 ROLLBACK（没货了）
COMMIT;
```

**生成商品详情写回。** 模型（ChatGPT 那类）在事务**外面**跑完，最后一条 `UPDATE products SET content=? WHERE id=?` 即可。单条语句自己就是事务。

**对账、抢最后一个名额。** 先 `SELECT ... FOR UPDATE` 把这行锁住，再按读到的值去写。避免两个请求都读到「还剩 1 个」。

事务要短：不要在事务里调大模型、上传文件、`sleep`。长任务先在外面做完，最后用很短的事务写库。锁拿得越久，别人等得越久。

## 不用事务的痛点，以及怎么解决

**扣了库存，插入订单失败。** 没有事务就留下脏数据。两步放进同一事务，失败就 `ROLLBACK`。

**最后一件被卖掉两次。** 两个请求都读到 stock=1。用 `UPDATE ... WHERE stock >= 1` 当闸门，或 `FOR UPDATE` 后再扣。不要先 `SELECT stock` 再在 Python 里减一写回——中间没有锁，两个请求都会以为自己抢到了。

**同一请求里两次读到的余额不一样。** 默认 RR 会钉住快照，这其实是特性。如果你希望每条语句都看到别人刚提交的值，改用 `READ COMMITTED`。

**报 `Deadlock found when trying to get lock`（死锁）。** 你锁了行 A 在等行 B，对方锁了行 B 在等行 A，形成环。多行一起锁时按 id 从小到大；事务尽量短；捕获死锁后把**整笔**重试，不要只重试一句 SQL。

**导入一百万行塞进一个事务，失败全滚、内存爆。** 按 1000～5000 行一段提交。

**`SELECT ... FOR UPDATE` 把整张表卡住。** `WHERE` 没走索引。先保证条件能用主键 / 唯一索引，见 [索引](../索引/索引.md)。

用两个终端演一遍最清楚（打开两个 mysql 窗口）：

```sql
-- 窗口 1
START TRANSACTION;
UPDATE products SET stock = stock - 1 WHERE id = 42;
-- 先不要 COMMIT

-- 窗口 2
SELECT stock FROM products WHERE id = 42;
-- 普通读：默认仍可能看到旧值（快照）

SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- 会卡住，直到窗口 1 提交或回滚
```

## 常见面试题

**什么是 ACID？下单时分别指什么？**

原子：订单和库存绑在一起。一致：提交后库存不为负。隔离：别人看不到做到一半。持久：`COMMIT` 之后断电也不丢。日常最容易踩的是隔离。

**MySQL 默认隔离级别？脏读、不可重复读、幻读？**

默认 REPEATABLE READ。脏读：读到别人没保存的修改。不可重复读：同一事务读同一行两次，中间被改了。幻读：同一条件查两次，行数变了。`READ UNCOMMITTED` 基本不用。

**快照读和当前读？**

普通 `SELECT` 是快照读：看到事务开始时的照片，不堵住别人写。`UPDATE` / `FOR UPDATE` 是当前读：要最新值，会锁行。所以上面窗口 2 的普通 SELECT 可能仍看到旧库存，`FOR UPDATE` 会卡住。

**InnoDB 的 RR 怎么防幻读？（面试常问，先混个脸熟）**

快照读靠 MVCC（多版本：每行留着旧照片）。当前读靠间隙锁：把「两行之间的空隙」也锁住，别人不能往这个范围内插入。你说「InnoDB 的 RR 大多能防幻读」即可，不必先把锁的种类背完。

**怎么避免超卖？为什么不能先 SELECT 再在应用里减？**

两个请求都读到 1，都写成 0。正确做法：`UPDATE ... SET stock = stock - 1 WHERE stock >= 1`，看影响行数；或先 `FOR UPDATE`。闸门在数据库，不在 Python。

**死锁怎么来的？怎么处理？**

互相等对方的锁，形成环。按 id 从小到大锁；事务短；捕获后重试整笔。

**为什么事务要短？一条 UPDATE 要不要显式开事务？**

锁拿得越久，别人等得越久。生成详情：模型在事务外跑完，最后一条 UPDATE 即可——单条语句自己就是事务。只有多步必须一起成功，才自己 `START TRANSACTION`。
