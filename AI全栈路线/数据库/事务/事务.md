# SQL 事务

> 目标：搞清楚「一组 SQL 为什么必须一起成功或一起失败」，以及两个事务同时跑时，彼此能看见什么。

默认按 **PostgreSQL** 讲。MySQL InnoDB 的差异会标出来。建议先看完 [索引](../索引/索引.md)，因为锁的粒度经常取决于有没有索引。

---

## 第 0 课：事务是什么

事务是一组必须当成一个整体的 SQL。要么全部提交，要么全部回滚，中间状态不能被别人当成最终结果。

最经典的例子是转账：

```sql
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;  -- 从 A 扣 100
UPDATE accounts SET balance = balance + 100 WHERE id = 2;  -- 给 B 加 100

COMMIT;   -- 两步都成功，才真正落盘
-- ROLLBACK;  -- 任何一步失败，两边都回到转账前
```

如果第一步成功、第二步挂了，却没有事务，A 的钱就蒸发了。

PostgreSQL 里，没写 `BEGIN` 的单条 SQL 自己就是一个事务：执行成功等于自动 `COMMIT`，失败等于自动 `ROLLBACK`。

## 第 1 课：ACID 用转账来记

| 字母 | 名字 | 转账时的意思 |
|---|---|---|
| A | Atomicity 原子性 | 扣款和入账必须一起成功或一起失败 |
| C | Consistency 一致性 | 转完之后，所有账户余额合计不变，约束（余额不为负、外键）仍然成立 |
| I | Isolation 隔离性 | 转账做到一半时，别人不能读到「A 已扣、B 还没加」 |
| D | Durability 持久性 | `COMMIT` 返回后，即使进程崩溃，这 100 块也不会丢 |

四个字母里，日常写业务最容易踩的是 **I（隔离）**。后面几课都围着它转。

## 第 2 课：三个并发问题

假设账户表里有一行：`id=1, balance=1000`。两个事务同时跑。

### 脏读 Dirty Read

事务 B 读到了事务 A **还没提交** 的修改。A 如果回滚，B 手里就是假数据。

```
A: UPDATE balance = 900   -- 还没 COMMIT
B: SELECT balance         -- 读到 900
A: ROLLBACK               -- 其实还是 1000
B 接下来按 900 做决定，就错了
```

PostgreSQL 默认隔离级别下 **不会脏读**。MySQL 的 `READ UNCOMMITTED` 会。

### 不可重复读 Non-Repeatable Read

事务 B 两次读同一行，中间被 A 改掉并提交了，两次结果不一样。

```
B: SELECT balance  → 1000
A: UPDATE balance = 900; COMMIT;
B: SELECT balance  → 900    -- 同一次事务里，同一行变了
```

### 幻读 Phantom Read

事务 B 两次按同一条件查，中间被 A **插入或删除** 了符合条件的行，行集合变了。

```
B: SELECT * FROM accounts WHERE balance > 500   → 3 行
A: INSERT 一条 balance=800; COMMIT;
B: SELECT * FROM accounts WHERE balance > 500   → 4 行
```

不可重复读是「同一行的值变了」；幻读是「行的数量变了」。

## 第 3 课：四个隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 | PostgreSQL 实际行为 |
|---|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | PG 会把它当成 READ COMMITTED |
| READ COMMITTED | 不会 | 可能 | 可能 | **PG 默认** |
| REPEATABLE READ | 不会 | 不会 | 理论上可能 | PG 用快照，实际也防幻读 |
| SERIALIZABLE | 不会 | 不会 | 不会 | 冲突时直接失败，让你重试 |

MySQL InnoDB 默认是 `REPEATABLE READ`。不要拿 MySQL 的默认级别去套 PostgreSQL。

切换级别：

```sql
-- 当前会话
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
-- ...
COMMIT;

-- 或者
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

选级别的实用标准：

- 普通查询、后台任务：`READ COMMITTED` 就够
- 对账、库存扣减、唯一名额：「先读再按读到的值去写」时，升到 `REPEATABLE READ` 或加行锁
- 必须看起来像「事务一个接一个执行」：`SERIALIZABLE`，并准备好捕获序列化失败后重试

## 第 4 课：PostgreSQL 怎么做到「读不堵写」

PostgreSQL 用 **MVCC（多版本并发控制）**。更新一行不是原地改，而是：

1. 保留旧版本给「还看不见这次修改」的事务读
2. 插入一个新版本给之后的事务读

每行（准确说每个版本）带着：

- `xmin`：创建这个版本的事务 ID
- `xmax`：删除 / 更新这个版本的事务 ID（0 表示还活着）

一个事务开始时会拿到一份 **快照**：哪些事务 ID 已经提交、哪些还在跑。读的时候只看「对自己可见」的版本。

所以：

- 读一般不加行锁，不会堵住别人写
- 写才会锁行
- 旧版本不会永远留着，`VACUUM` 负责清掉没人需要的版本

> MySQL InnoDB 也是 MVCC，但实现不同：undo log 里保留旧值，读已提交 / 可重复读靠 Read View。结果类似：普通 SELECT 不堵 UPDATE。

## 第 5 课：真正会锁的语句

普通 `SELECT` 在 PostgreSQL 里几乎不锁业务行。下面这些会：

```sql
-- 读出来并且锁住，不让别人改
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- 锁住但不那么狠，允许别人也 SELECT FOR SHARE
SELECT * FROM accounts WHERE id = 1 FOR SHARE;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
DELETE FROM accounts WHERE id = 1;
```

库存扣减的正确姿势（避免超卖）：

```sql
BEGIN;

SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- 现在别人改不了这行

-- 应用层判断 stock >= 1 之后：
UPDATE products SET stock = stock - 1 WHERE id = 42;

COMMIT;
```

更短的写法，让数据库自己判断：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock >= 1;

-- 检查受影响行数：0 就是库存不够
```

**索引在这里很关键。**

```sql
SELECT * FROM accounts WHERE email = 'bob@x.com' FOR UPDATE;
```

- 有 email 唯一索引：只锁这一行
- 没有索引：可能扫表，锁很多行，甚至在某些实现里接近锁表

写 `FOR UPDATE` 的 `WHERE` 必须能走索引。

## 第 6 课：死锁

两个事务各拿一把锁，再等对方手里那把：

```
事务 A: 锁住 id=1，接着要锁 id=2
事务 B: 锁住 id=2，接着要锁 id=1
→ 互相等，直到数据库选一个当牺牲品，把它 ROLLBACK
```

PostgreSQL 会报：

```
ERROR: deadlock detected
```

常见防法：

1. 多个行一起锁时，按固定顺序锁（都按 id 从小到大）
2. 事务尽量短，不要在事务里调 HTTP、睡几秒
3. 捕获死锁错误后重试整个事务

## 第 7 课：提交之后才算数

`COMMIT` 成功返回，才有持久性。崩溃恢复靠 WAL（预写日志）：先把变更写进日志，再改数据页。

日常要注意的三点：

1. **事务不要包太大。** 一次导入 100 万行塞进一个事务，失败就全滚，内存和锁都会很难看。批量导入按几千行一段提交。
2. **DDL 也在事务里。** PostgreSQL 里 `ALTER TABLE` 可以 `ROLLBACK`。MySQL 很多 DDL 会隐式提交，回滚不了。
3. **应用层要处理失败。** `SERIALIZABLE` 冲突、死锁、唯一约束冲突，都该重试或明确告诉用户，而不是吞掉错误。

## 第 8 课：用 psql 自己演一遍

开两个终端，都连上同一个库。

终端 1：

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 先不要 COMMIT
```

终端 2：

```sql
SELECT balance FROM accounts WHERE id = 1;
-- READ COMMITTED 下你还是看到旧值（A 没提交）

SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 这行会卡住，直到终端 1 COMMIT 或 ROLLBACK
```

再试一次：终端 1 `COMMIT` 后，终端 2 的普通 `SELECT` 立刻变成新余额；如果终端 2 一开始就开了 `REPEATABLE READ` 事务，它在自己 `COMMIT` 前仍会看到旧快照。

## 速查

| 记住这句 | 含义 |
|---|---|
| 事务 = 一组 SQL 的边界 | `BEGIN` 到 `COMMIT` / `ROLLBACK` |
| ACID 里最常踩的是隔离 | 并发时彼此能看见什么 |
| PG 默认 READ COMMITTED | 每次语句看到最新已提交数据 |
| 普通 SELECT 不堵 UPDATE | 因为 MVCC 读的是版本，不是锁 |
| `SELECT FOR UPDATE` 才锁行 | 先读后写的业务用它，WHERE 必须走索引 |
| 死锁不是异常状态，是并发常态 | 固定锁顺序 + 短事务 + 重试 |
