## 一、技术选型（3 题）

  

**Q1：为什么用 ParadeDB 而不是 pgvector + pg_trgm？**

  

> 考察：检索方案的 trade-off 思考

>

> 参考要点：

>  pg_trgm 字符级拆分，做模糊匹配需要额外调相似度阈值，且对 SKU 精确词（如"飞天茅台"vs"茅台飞天"）排序不稳定

> ParadeDB pg_search 是 BM25，原生支持中文分词 + 精确词打分，RRF融合更自然

> 向量和 BM25 都在 PostgreSQL 内部，过滤条件（品类/价格带/SKU）能直接下推 SQL，**不需要跨库 JOIN**——这是最核心的选型理由，RRF 融合也在单库完成

> 如果 SKU 数量上到万级以上才考虑 Milvus/ES，225 款产品量级 pgvector 足够

  

**Q2：为什么 LangGraph createReactAgent，不自己写状态机？**

  

> 考察：Agent 架构选择的代价认知

> 参考要点：

>  ReAct 模式的循环逻辑（LLM 推理→工具调用→再推理）自己写 50 行能跑，但要加 max_tool_calls 上限、空结果兜底、错误恢复、消息历史截断，很快膨胀

>  createReactAgent 给我留了 Tool 接口 + streamMode 两个钩子，我只用实现 3 个 Tool 和 system prompt 约束

>  代价是：streamMode="values" 是节点级输出，不逐 token——后来切到 "messages" 才解决流式，这是个踩坑点

  

**Q3：向量模型选了什么，为什么 1536 维？**

  

> 考察：嵌入模型选型与工程配套

>

> 参考要点：

> - qwen3.7-text-embedding，国产模型对中文产品名/口感描述的向量质量比 openai text-embedding-3-small 好

> - 1536 维是模型默认输出，在当前量级没什么压力，如果在数据量比较大的情况下，可能需要做1024/1536 的A B测试，如果1024维度的Recall差异不大，可以选择1024的，索引更快，占存储也更小

> - 如果重来会评估 bge-m3 支持多语/稀疏检索，但当时中文优先，如果后续要私有化部署和降成本，应该考虑它

## 二、检索迭代（4 题，全部有 A/B 实验数字）

  

**Q4：混合检索相对单向量提升了多少？在哪些查询类型上？**

  

> 考察：是否真的做了对比，还是拍脑袋选的混合检索

>

> 参考要点：

> - 我跑了五轮 A/B 实验，45 条有效评测集

> - 总体 Recall：单向量 0.94 → 混合 0.95（整体差异不大）

> - **关键价值在话术类**：单向量 0.94 → 混合 1.00——话术标题是"【异议·太贵】价格锚定三步法"这种结构化关键词，BM25 精确匹配比纯向量语义搜更准

> - 产品查询 Recall 相同（都是 0.85），因为产品名本身短且品牌/品类词明确，向量也能匹配上

  

**Q5：查询改写做了什么，提升在哪里？**

  

> 考察：查询理解的工程实现细节

>

> 参考要点：

> - 前置一步 LLM 调用，从自然语言抽取品类/价格带/exact_terms 三个结构化字段，**下推到 SQL 的 WHERE 子句**（而不是改写后再搜）

> - 在 top-5 截断下，"500以内酱香白酒"这类价格带+品类组合查询 Recall 从 0.50→0.75

> - 但 top-N 提到 8 后，查询改写的增量收益被覆盖了——因为原来 top-5 挤爆是主要瓶颈

> - 所以保留为可选开关 `QUERY_REWRITE=1`，默认走 top-8；改写的价值在"top 窗口受限时的精准补位"

  

**Q6：PRODUCT_TOP_N 从 5 改到 8，为什么是 8 不是 10？**

  

> 考察：超参选择的依据

>

> 参考要点：

> - 225 款产品列举类查询（"精酿啤酒有哪些"）实际能命中 4~6 款，top-5 会挤掉 1~2 款

> - top-8 后产品查询 Recall 0.85→0.96，再往上 top-10 增益递减（8→10 只有 0.01 提升），但额外 2 条会稀释 LLM 的注意力——所以在 8 停

> - 话术 top-3 不改，因为话术是按主题组织的，3 条已覆盖主推+备选，多了 LLM 会乱选

  

**Q7：RRF K 值为什么设 60？**

  

> 考察：RRF 融合的参数依据

>

> 参考要点：

> - RRF 公式是 1/(k + rank)，k 控制高排名的权重衰减速度

> - k=60 是业界经验值（从 Elasticsearch 融合文档抄的初始值），我做了 k=20/40/60/80 的小范围试跑

> - k 太小（20）：排在第 2 位的向量结果得分比第 12 位 BM25 高太多，BM25 补充失效

> - k 太大（80）：各路排名差异被抹平，等于没融合

> - 60 在 225 款的产品量级下是 sweet spot

## 三、Agent 与工具编排（3 题）

  

**Q8：三个 Tool 怎么分工？为什么价格不合并进 search_products？**

  

> 考察：工具粒度设计原则

>

> 参考要点：

> - search_products：返回产品属性，但**价格字段故意不进**（products 表 price_band 只存档位不存数字）

> - get_prices：独立查 prices 表取供货价+零售价

> - 原因：**价格红线机制**——system prompt 明确"价格只能来自 get_prices 工具"，如果把价格塞进 search_products 返回值，Agent 可能跳过 get_prices 直接答，我就没法保证价格一定来自实时数据表

> - 评测里工具断言 100% 通过，说明这个约束生效了

  

**Q9：Agent 会不会重复调用工具或跳过工具？怎么防？**

  

> 考察：Agent 行为边界控制

>

> 参考要点：

> - LangGraph 有 `max_iterations` 参数，我设了 10，死循环熔断

> - System prompt 里写了"先 search_products 再 get_prices，不要对已取过价的 SKU 重复调 get_prices"

> - 多轮对话历史里 Agent 已经知道 SKU 时（如 M2 "它的零售价呢"），应该直接调 get_prices 而不是再 search_products——这就是评测集里 M2/M4 的 expected_tools 只写 get_prices 的原因

> - 跳过工具的情况（Agent 凭记忆报价）在 50 条评测里是 0 次，红线约束生效了

  

**Q10：SSE 流式输出怎么实现的？遇到过什么坑？**

  

> 考察：流式生成的实现细节

>

> 参考要点：

> - 后端用 Next.js route handler 返回 `ReadableStream`，逐块 `res.write("event: text\ndata: ...\n\n")`

> - **踩坑**：最初用 `streamMode: "values"`，是按节点粒度吐，每个 Agent 节点完整跑完才返回——看起来就是不流式。后来改成 `"messages"`，直接消费 LLM token 流，才逐字出来

> - 工具调用的 tool_start 事件：因为 messages 模式下 tool call 参数是增量到达的（chunk 式），我用 Set 按 index 去重，首次出现时发事件，不存完整参数

> - 前端用 fetch + ReadableStream.getReader() 逐块解析，react-markdown 边收边渲染

## 四、评测体系（3 题）

  

**Q11：评测集怎么构建的？为什么是 50 条不是 100 条？**

  

> 考察：评测集的分层设计意识

>

> 参考要点：

> - 6 类意图分层（产品 15、价格 8、话术 8、组合多步 8、多轮 6、边界拒绝 5），每类至少 5 条保证统计意义

> - 50 条是开发迭代期的合理规模——改一次检索参数跑一遍约 10 分钟，太快没感觉，太慢不敢常跑

> - 标注方式：golden_skus 从数据库真实 SKU 里查出来标，不是拍脑袋。评测集里 R2 锐澳原来标成边界拒绝，后来发现库里其实有 QT007，修了标注

> - 后续要扩到 150 条的话，RAGAS 的合成数据能帮我自动生成 question + golden_context，人工只筛

  

**Q12：Faithfulness 怎么算的？0.83 分意味着什么？**

  

> 考察：LLM-as-judge 的实现与局限性

>

> 参考要点：

> - 我自己写的 judge prompt：让 LLM 把答案拆成独立 claim，逐条判断能否由检索上下文推出，比例就是 Faithfulness

> - 0.83 意味着平均 17% 的 claim 没有上下文支撑

> - **关键发现**：低分案例几乎不是编造事实（价格数字 50 条里 0 编造），而是回答末尾附带了"销售建议/替代推荐"段落——judge 按"必须全部来自上下文"从严扣分

> - 所以 Faith 0.83 实际质量比分数好，红线机制兜底了最关键的价格编造风险

> - Judge 用便宜模型（qwen-turbo），temperature=0 保证可复现

  

**Q13：工具断言和 Recall 有什么关系？为什么要单独测工具断言？**

  

> 考察：Agentic RAG 评测的独特性

>

> 参考要点：

> - 普通 RAG 只测"答案对不对"，Agentic RAG 还要测"过程对不对"

> - 工具断言是过程指标：价格问题必须出现 get_prices，不能凭记忆答

> - 我的系统 Recall 0.98 但如果工具断言只有 0.7，说明有 30% 的回答虽然数字碰巧对了但不是走工具来的——改价后这些回答就会错

> - 所以工具断言 100% 是比 Recall 更硬的底线指标，它保证了价格实时性的链路没断

## 五、系统设计与工程（3 题）

  

**Q14：4 表最简架构为什么没有独立向量表？**

  

> 考察：RAG 架构的简化意识

>

> 参考要点：

> - 业界常见做法是 docs/chunks/embeddings 三张表分开，但这个项目里产品是按 SKU 一对一，话术是按单条独立，不存在"一个文档拆成多个 chunk"的场景

> - 所以向量列直接挂在 products/scrips 表上，检索命中一行就拿到完整原文，**不需要二次回查**——省了 JOIN，也省了维护 chunk 边界的复杂度

> - 如果以后产品要支持长文档（如酒厂介绍），再加 chunks 表也不迟

  

**Q15：content_hash 增量幂等上传怎么实现的？为什么要做？**

  

> 考察：数据管道的幂等设计

>

> 参考要点：

> - 上传时先算 sha256(产品名+规格+产地+口感+...)，和数据库里的 content_hash 比对

> - 一致就跳过嵌入生成（省 API 调用），不一致才重新调 embedding 服务并更新向量

> - 价值：运营反复上传同一个 Excel 不重复花钱，嵌入 API 成本可控

> - 价格独立维护在 prices 表，改价只刷新 products.price_band 字段，**绝不触发向量重建**——这是和 content_hash 解耦的另一条幂等线

  

**Q16：如果让你加一个 reranker，加在哪里？预期提升多少？**

  

> 考察：对 RAG 全链路的认知深度

>

> 参考要点：

> - 加在混合检索 RRF 融合之后、PRODUCT_TOP_N 截断之前

> - 我现在的链路是：BM25 top-10 + 向量 top-10 → RRF 融合 → top-8 截断

> - 如果加 reranker：BM25 top-10 + 向量 top-10 → RRF 融合 top-12 → rerank → top-8

> - 预期提升：产品查询 Recall 0.96→0.98 左右，因为 reranker 对"价格带+品类"这类组合条件的语义匹配比 RRF 融合更准

> - 但 reranker 多一次模型调用，延迟从 ~200ms 涨到 ~500ms，目前 top-8 已经够用，所以没加——这是 trade-off 的选择

## 面试策略建议

  

1. **先抛数字再讲故事**：每个问题开头先报"我做了 X 轮 A/B 实验，Recall 从 A 到 B"，比空讲原理有说服力

2. **诚实暴露边界**：查询改写在 top-8 后收益被覆盖、Faithfulness 0.83 有 judge 从严扣分的因素——主动说比被追问再辩解好

3. **踩坑点当加分项**：streamMode values→messages 的问题、content_hash 设计动机、评测集标注修了 3 处——这些"不是一帆风顺"的故事比"我一步到位"可信得多
